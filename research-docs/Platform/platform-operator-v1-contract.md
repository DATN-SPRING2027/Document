## 1. Purpose

Define a reviewable V1 source of truth for DATN-295–300: permission names, operations, scopes, visibility, authorization, audit and bootstrap rules. Avoid widening DATN-79/A-04 authority accidentally.

## 2. Scope and evidence labels

V1 intends one platform role with the full set of **approved Platform Administration V1 permissions**, with no tiers or role hierarchy. “Full” means the finite approved operation set, not wildcard access, tenant-content access, authentication bypass or unrestricted CRUD.

- **[CONFIRMED]** Directly supported by accepted Jira decisions, approved docs or current code.
- **[DERIVED]** Follows from confirmed evidence without adding policy.
- **[PROPOSED]** New policy requiring owner/security approval before implementation.
- **[CONFLICT]** Sources disagree; implementation must wait for resolution.
- **[APPROVED POLICY; NOT RUNTIME]** A KeyT-approved authorization or response policy recorded in §24; it does not enable runtime permissions, endpoints or UI.
- **[DEFERRED]** Explicitly excluded from active V1; do not implement or render it.
- **[BLOCKED]** Required owner decision or evidence is missing; implementation must wait.
- **Outside active catalog / implementation blocked** The operation is not in the active V1 catalog until an authorized domain owner records `ACTIVE` with complete semantics or explicitly `DEFERRED FROM V1` with rationale/evidence. Missing approval is not a final operation status or deferral.

This task is documentation only. No permission here is added to runtime authorization.

**[APPROVED POLICY; NOT RUNTIME]** The V1 policy set contains exactly the 3 unchanged DATN-79/A-04 codes plus the 37 codes listed in §5.2. A full V1 operator grant is the exact set of 40 distinct, current assignments at `PLATFORM` scope; any partial, duplicate, malformed, expired, revoked, future-dated, wrong-scope, or extra platform-code set fails closed for the 37 new permissions. This set-level qualification is derived from D1 and must be checked from current server-side evidence, not a role name or token claim. The three existing A-04 operations retain their current exact-code behavior for existing standalone assignments; those assignments are not rewritten or automatically backfilled, and a standalone A-04 assignee does not thereby become a full V1 operator. Granting or revoking the full 40-code set is all-or-nothing and atomic. The 37 codes are not added to runtime by this document.

## 7. Actor → Action → Resource → Scope

1. **Authenticate:** validate access token, current user state and revocation as the existing auth service does.
2. **Identify actor:** use the verified token subject; never trust a client-supplied actor ID.
3. **Resolve authority:** require the exact current permission. A role name alone, stale token claim or wildcard cannot authorize.
4. **Resolve target:** load target and parent relationships from the authoritative service/store. Client IDs are lookup inputs only.
5. **Evaluate state:** validate Organization/Project relationship, resource lifecycle, current version, and operation-specific invariants.
6. **Allow or deny:** fail closed on invalid/missing authorization evidence. Return 404 for concealment only when the resource class is listed by DEC-ACCESS-10; otherwise follow the applicable authorization policy.
7. **Audit mutation:** persist the required audit record with the operation outcome.

Grant scope is PLATFORM for these platform permissions. Target scope remains distinct: PLATFORM, Organization, Project, or resource as shown per operation. A platform grant does not convert target scope, create Organization membership, or bypass Project ACL/content checks.

## 12. Audit Contract

**[APPROVED POLICY]** The operator interface/API is append-only: this role cannot update or delete audit history. Every privileged mutation must fail closed. The system must not report mutation success unless the required audit event is durably recorded. Secret, credential, raw payload and tenant content are excluded from responses and audit metadata.

**[CURRENT EVIDENCE]** Existing Organization provisioning writes its audit event transactionally. The existing platform audit endpoint reads a bounded projection; it is not a general-purpose operator mutation log. Code inspection does not prove immutable storage or a complete grant/revoke producer.

**[DERIVED CONTRACT REQUIREMENT]** A state mutation and its required audit event must share one durable commit boundary. For an operation backed by the same transactional datastore, commit them atomically; if audit persistence fails, roll back the mutation and return no success. For an asynchronous or external side effect, the accepted command/intent and its audit event must be durably recorded together before dispatch; if the operation cannot provide that boundary and reconcile retries safely, it remains outside the active catalog. This is an outcome requirement, not a claim that a universal outbox exists. The current A-04 Organization provisioning follows the same-datastore transaction pattern and its tests show audit failure rolls back the Organization, membership and role assignment. Whether failed attempts and denials themselves need audit events remains an owner decision.

**[BLOCKED FOR OWNER DISPOSITION]** Security/IAM must approve retention period and enforcement boundary. Security/Audit/domain owners must define per-operation event producers, required actor/target/action/result/time/request identifiers, reason requirements, redaction, read/export/denial treatment, and audit-store durability/retention enforcement evidence. The approved fail-closed policy is binding, but this document does not claim database-level tamper-proofing or a deployed universal outbox.

Never include passwords, API keys, tokens, private keys, MFA values, raw job payloads, document content, chat history or retrieved RAG text. Detailed per-operation fields and test oracles belong in the approved operation records.

## 14. Bootstrap Strategy

The policy controls below are approved, but Security/IAM has not named the issuer/executor or approved the operational runbook. This section is a boundary, not authority to bootstrap an operator.

1. **Identity:** recipient must be an existing verified ACTIVE user. No hidden user or production seed.
2. **Issuer:** Security/IAM must name an authorized issuer and executor, the identity source for both, and the evidence/change record. Until then first grant is BLOCKED.
3. **Grant/revoke authority:** the existing PLATFORM_OPERATOR role has no grant/revoke operation or public API. No current operator may self-grant, and no evidence authorizes an operator to grant or revoke another operator. Grant/revoke must use the separately approved Security/IAM-controlled issuer path; its exact actor, approval chain and executor are an external decision.
4. **Assignment:** use the exact 40-code set from §5.2; the full grant is atomic and all-or-nothing. No partial set may resolve as PLATFORM_OPERATOR. Do not rewrite or auto-backfill standalone A-04 assignments.
5. **Self-grant:** no issuer may grant authority to itself. Do not expose public self-service bootstrap.
6. **Last operator:** do not silently prevent or permit revocation/suspension of the final operator. Security/IAM must decide whether a last operator may be removed and specify the authorized recovery path that avoids both lockout and an undocumented bypass. Until signed, last-operator removal is not an implementable policy.
7. **Concurrency and replay:** grant/revoke must be all-or-nothing and prevent duplicate or racing partial state. Replaying the same logical request must not create duplicate assignments or apply a state transition twice; concurrent requests must serialize or use a version/CAS check and return one authoritative complete state. A reused request key with different payload must be rejected as a conflict where a key-based API exists. Exact keys, storage indexes and retry response bodies remain DATN-295/296 implementation details. Attempt-audit behavior remains a Security/Audit decision.
8. **Audit and persistence:** assignment writes and their required grant/revoke audit event share the same durable commit boundary. For a same-database transaction, commit both atomically; on audit failure, roll back every assignment change and report no success. For any different storage boundary, the assigned owner must prove an equivalent durable intent/audit mechanism before activation. Retention, audit event schema and enforcement remain owner decisions.
9. **Recovery:** recovery for loss of the only operator, revoke, rollback and post-action verification must be in the signed Security/IAM runbook.
10. **No bypass:** no Break-glass, hidden admin, credential bypass, unattended default account or production seed.

**Readiness:** no bootstrap API, seed or production assignment may be implemented until Security/IAM names the issuer and executor, signs identity evidence and the complete recovery runbook, and the implementation can prove atomic exact-set assignment plus durable audit. “Use a manual process” alone is not a runbook.

### Approved policy decisions

1. **Exact permission membership.** PLATFORM_OPERATOR V1 membership is exactly the three existing A-04 codes plus the 37 codes already enumerated in §5.2. No wildcard or additional code is approved. Keep all three existing codes and semantics unchanged. The approved 37-code set is policy only; it is not yet present in runtime.

The full 40-code operator grant and revoke must be atomic and all-or-nothing. A partial/corrupt set does not resolve to the full PLATFORM_OPERATOR set. This approves the broad baseline only; the DEC-ACCESS-10 owner still must decide the missing-versus-forbidden behavior and concealment class for each resource. Do not invent stable code names or resource classes here.
5. **Audit invariants.** The operator interface/API cannot update or delete audit history. Every privileged mutation fails closed: do not return success unless the required event is durable. As the implementation contract derived from this invariant, state and audit must share a durable commit boundary; an external side effect needs an atomically recorded durable intent/audit before dispatch or stays outside the active catalog. This matches the current A-04 Organization transaction precedent; it does not select or claim a universal outbox implementation. Never include secrets, credentials, raw payloads or tenant content in responses/audit metadata.
