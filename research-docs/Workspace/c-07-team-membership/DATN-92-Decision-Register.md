## 1. Status vocabulary

- **APPROVED — VERIFIED:** exact decision and authority are supported by evidence within the stated scope.
- **APPROVED — CONDITIONAL:** the approval is effective only when its named dependency is verified.
- **RECOMMENDED — AWAITING APPROVAL:** a complete default is proposed; it is not approved.
- **DEFERRED:** no behavior should be enabled until an owner selects a policy.
- **BLOCKED BY DEPENDENCY:** a separate technical review/implementation/merge is required.
- **SUPERSEDED:** retained only for history; a traceable correction controls.

`Jira Done`, a PR review, this Draft PR, or a local proposal is not proof of approval.

## 4. Alternatives and compatibility summary

- **Authorization:** action-specific permissions avoid broad grants and preserve current Project-scoped role assignment. A colon/dot alias is rejected because it makes grants ambiguous; existing Team Foundation authorization needs a coordinated, separately reviewed canonicalization.
- **Parent lifecycle:** status-only checks can restore stale access after reactivation. Cascade delete conflicts with the no-cascade C-04 direction and destroys direct admission history. Generation snapshots plus fences implement the approved security goal, but require all parent writers and races to be reviewed.
- **Identity/history:** reusing an ID directly contradicts approved new-ID rejoin. Separate retained admissions with one active pair preserve identity and history but require changing the current unique index in a separate DB PR.
- **Audit:** direct same-session audit matches the approved invariant and existing Project pattern. Outbox relay changes the atomicity guarantee and requires explicit amendment. No policy duration is invented.
- **GET:** leaving the existing shared draft unchanged avoids a unilateral shared API deletion; the C-07 OpenAPI and PR must expose no GET, and owner must clarify its independent disposition.
